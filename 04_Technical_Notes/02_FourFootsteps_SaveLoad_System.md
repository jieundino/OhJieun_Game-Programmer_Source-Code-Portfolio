# 네 발자국 — Save / Load Reliability System

> **Atomic Write · Type Preservation · Legacy Recovery**

## 1. 문서 목적

플레이어의 선택·조사·이벤트·엔딩 상태를 안정적으로 저장하고, 강제 종료·타입 불일치·구버전 데이터 상황에서도 전체 복원이 실패하지 않도록 구성한 Save/Load 시스템을 정리합니다.

---

## 2. 문제 정의

- 원본 파일에 직접 쓰는 도중 종료되면 저장 파일 전체가 손상될 수 있음
- `Dictionary<string, object>`는 역직렬화 후 숫자와 복합 타입이 원래 타입으로 돌아오지 않을 수 있음
- 저장 구조 변경 후 이전 버전 데이터를 읽지 못할 수 있음
- 내부 상태만 복원하고 UI·오브젝트 상태를 갱신하지 않으면 화면과 데이터가 달라질 수 있음

---

## 3. 요구사항

- 저장 중 실패해도 이전 정상 파일을 보호할 것
- 플레이 상태와 타입 정보를 함께 보존할 것
- 일부 데이터가 손상되어도 가능한 범위에서 복구할 것
- 구버전 저장 데이터를 fallback 경로로 읽을 것
- 내부 상태 복원 이후 UI와 오브젝트를 갱신할 것
- 엔딩 조건에 필요한 상태가 저장 전후 동일할 것

---

## 4. 저장 흐름

```text
현재 게임 상태 수집
→ 값 데이터와 타입 정보 직렬화
→ 임시 파일(.tmp)에 기록
→ 기존 파일을 .bak으로 백업
→ 임시 파일을 원본 경로로 교체
→ 교체 실패 시 Delete / Move fallback
```

## 5. 불러오기 흐름

```text
원본 저장 파일 확인
→ JSON 파싱
→ 타입 정보에 따라 값 복구
→ 복합 타입 전용 복구
→ 실패 시 백업·레거시 fallback
→ 내부 상태 적용
→ UI·오브젝트·현재 이벤트 갱신
```

---

## 6. 핵심 구현

### 6.1 Atomic Write

원본 파일을 바로 덮어쓰지 않고 임시 파일에 완전히 기록한 뒤 교체했습니다. 교체 전에 기존 파일은 `.bak`으로 보존했습니다.

### 6.2 타입 정보 분리

변수 값과 타입 정보를 별도로 저장해 `int`, `bool`, 문자열과 복합 타입을 복원할 수 있도록 했습니다.

### 6.3 복합 타입 fallback

`Dictionary<int, bool>` 등 특정 복합 타입은 전용 복구 경로를 두고, 잘못된 값 하나가 전체 Save/Load 실패로 이어지지 않도록 예외 처리를 적용했습니다.

### 6.4 레거시 데이터 복구

현재 형식 파싱이 실패하면 이전 저장 구조를 확인하고 가능한 값을 새 구조로 변환하도록 구성했습니다.

### 6.5 상태와 화면 동기화

내부 상태를 먼저 복원한 뒤 현재 이벤트, UI와 상태 기반 오브젝트 이미지를 갱신했습니다.

---

## 7. 검증 항목

| 항목 | 확인 내용 |
| --- | --- |
| 정상 저장 | 현재 상태가 JSON으로 기록되는가 |
| 강제 종료 대비 | 임시 파일 기록 전 원본이 보호되는가 |
| 백업 | 교체 전 이전 정상 파일이 `.bak`으로 유지되는가 |
| 타입 복원 | 숫자·bool·복합 타입이 원래 의미로 복원되는가 |
| 레거시 데이터 | 이전 버전 파일에서 가능한 값이 복구되는가 |
| 일부 손상 | 하나의 파싱 실패가 전체 Load 실패로 확산되지 않는가 |
| 상태 동기화 | 불러오기 후 UI와 오브젝트가 내부 상태와 일치하는가 |
| 엔딩 분기 | 선택·조사·책임 상태가 동일한 결과를 만드는가 |

---

## 8. 구현 결과

- 쓰기 실패 시 원본 저장 파일의 손상 가능성을 낮췄습니다.
- 값과 타입 정보를 분리해 상태 복원 정확도를 높였습니다.
- 복합 타입과 구버전 데이터의 fallback 경로를 구성했습니다.
- 불러오기 이후 내부 상태와 화면 표현을 동기화했습니다.

---

## 9. 한계 및 개선 방향

- PlayerPrefs와 파일 저장이 혼재하면 데이터 버전 관리가 어려울 수 있음
- 데이터 마이그레이션 규칙이 늘어나면 SaveManager 책임이 커질 수 있음
- 저장 데이터 버전과 스키마 검증을 더 명시적으로 관리할 필요가 있음

### 개선 방향

- `saveVersion`을 기준으로 한 단계별 Migration Pipeline
- 저장 DTO와 런타임 객체의 명확한 분리
- 타입별 단위 테스트와 손상 파일 테스트 자동화
- 저장 데이터 검사 및 복구 결과를 표시하는 디버그 도구

---

## 10. 연구개발 직무와의 연결점

정상 동작뿐 아니라 강제 종료, 타입 변경, 데이터 손상과 구버전 호환이라는 실패 조건을 정의하고, 복구 정책과 후속 검증 항목을 구조화한 경험입니다.
