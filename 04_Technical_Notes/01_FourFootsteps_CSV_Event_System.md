# 네 발자국 — CSV 기반 Event / Result System

> **Data-driven Content · Condition Evaluation · Result Execution**

## 1. 문서 목적

대사, 선택지, 이벤트 조건과 결과 실행을 CSV와 ID 기반으로 분리하고, 조건 판정과 실제 동작 실행을 독립된 책임으로 구성한 과정을 정리합니다.

---

## 2. 구현 배경

내러티브 콘텐츠에서는 기획 수정과 이벤트 추가가 반복됩니다. 이벤트를 코드에 직접 작성하면 수정마다 프로그래머가 개입해야 하고, 조건 판정·대사·연출·상태 변경이 한 클래스에 집중될 수 있었습니다.

따라서 콘텐츠 데이터는 CSV로 관리하고, 런타임 코드는 ID를 해석해 조건을 평가하고 결과를 실행하는 구조가 필요했습니다.

---

## 3. 요구사항

- 대사, 선택지, 조건과 결과를 데이터로 관리할 것
- Event ID와 Result ID로 실행 관계를 연결할 것
- AND / OR 조건을 구분할 것
- 독립 결과와 순서 의존 결과의 실행 방식을 분리할 것
- 콘텐츠 수정 시 실행 코드 변경 범위를 줄일 것
- 동시에 발생한 대사 요청의 순서를 보장할 것

---

## 4. 시스템 구조

| 시스템 | 책임 |
| --- | --- |
| `DialogueManager` | 대사 출력, 선택지 표시, Queue 기반 요청 순서 제어 |
| `EventManager` | CSV 파싱, 현재 상태와 조건 비교, 실행 모드 결정 |
| `ResultManager` | Result ID에 따른 변수·대사·연출·씬·오브젝트 동작 실행 |

```text
플레이어 입력 또는 이벤트 요청
→ EventManager 조건 판정
→ 실행 가능한 EventLine 선택
→ Instant / Sequential 모드 결정
→ ResultManager 결과 실행
→ 상태·대사·연출 갱신
```

---

## 5. 핵심 구현

### 5.1 CSV와 Dictionary

- Event ID별로 복수의 EventLine 저장
- 동일 ID가 존재하면 조건·결과 묶음을 추가
- Result 정의를 ID로 조회
- 콘텐츠 데이터와 실행 코드를 분리

### 5.2 조건 판정

- 조건이 없으면 즉시 실행
- AND 조건은 모든 조건을 만족할 때 실행
- OR 조건은 하나 이상 만족할 때 실행
- 조건을 만족한 첫 EventLine의 결과를 실행

### 5.3 실행 모드

- `Instant`: 독립적인 결과들을 모두 바로 실행
- `Sequential`: 앞선 결과가 완료된 뒤 다음 결과 실행

### 5.4 Function-wrapped Result

파라미터가 포함된 Result는 ID 패턴을 해석해 코드 함수로 연결했습니다. 이를 통해 단순 데이터 정의만으로 표현하기 어려운 결과를 처리했습니다.

### 5.5 Dialogue Queue

대화 진행 중 새로운 요청이 들어오면 기존 대화를 교체하지 않고 Queue에 저장해 현재 대화 종료 후 순차 실행했습니다.

---

## 6. 검증 항목

| 항목 | 확인 내용 |
| --- | --- |
| CSV 파싱 | Event ID와 Result ID가 올바르게 등록되는가 |
| 조건 판정 | AND / OR가 현재 상태와 일치하는가 |
| EventLine 선택 | 조건을 만족한 첫 분기만 실행되는가 |
| Instant | 독립 결과가 대기 없이 실행되는가 |
| Sequential | 결과가 정의된 순서로 완료되는가 |
| Dialogue Queue | 동시 요청이 기존 대사를 덮어쓰지 않는가 |
| 상태 반영 | 선택 결과가 후속 이벤트와 엔딩에 반영되는가 |

---

## 7. 구현 결과

- 기획 데이터를 실행 코드에서 분리했습니다.
- 조건 판정과 결과 실행의 책임을 구분했습니다.
- 결과의 병렬·순차 실행 정책을 명시했습니다.
- 여러 시스템의 대사 요청 순서를 Queue로 제어했습니다.
- 콘텐츠 추가와 수정 시 기존 코드의 변경 범위를 줄였습니다.

---

## 8. 한계 및 개선 방향

### 한계

- 단순 `Split(',')` 방식은 따옴표로 감싼 쉼표 필드에 취약할 수 있음
- 존재하지 않는 Result ID와 중복 ID를 런타임 이전에 확인하기 어려움
- Result 유형이 늘어나면 `ResultManager`의 분기가 커질 수 있음
- 복잡한 Sequential 실행의 취소·인터럽트 정책이 명시적이지 않음

### 개선 방향

- 정식 CSV parser 또는 데이터 형식 규칙 검증 도입
- Unity Editor 기반 Event Data Validator 구현
- Result 실행을 Command/Strategy 클래스로 분리
- ID 중복, 누락 참조와 잘못된 실행 모드의 사전 검사
- 실행 취소와 디버그 로그를 포함한 명시적 실행 컨텍스트 도입

---

## 9. 연구개발 직무와의 연결점

- 기획 요구사항을 데이터 구조와 실행 파이프라인으로 변환
- 반복 수정이 예상되는 기능의 확장 지점 설계
- 실행 순서와 동시 요청 충돌을 정책으로 정의
- 현재 구조의 제약을 분석하고 에디터 검증 도구라는 후속 과제로 구체화
