# 필연과 우연 — ActionPointManager State Flow

> **Project:** &lt;필연과 우연&gt;  
> **Role:** Client / System Programmer  
> **Contribution:** 행동력·날짜 진행 시스템 설계·구현 및 반복 입력·상태 예외 검증

> **State Validation · Shared Flow · Room-specific Rules**

## 1. 문서 목적

행동력 검증, 차감, 하트 UI 갱신, 날짜 전환과 Room별 특수 규칙을 하나의 상태 흐름으로 관리한 구조를 정리합니다.

---

## 2. 문제 정의

조사 오브젝트와 퍼즐을 빠르게 반복 조작하면 하나의 행동이 여러 번 처리되어 행동력이 중복 차감될 수 있었습니다. 행동력은 UI, 날짜 전환, 시계·페이지 연출, BGM과 후속 이벤트에 연결되어 있어 하나의 상태 오류가 전체 진행에 영향을 줄 수 있었습니다.

Room1은 행동력 회복 이벤트 없이 기본 소모와 날짜 전환 흐름만 관리했고, Room2는 특정 상호작용을 통해 행동력 회복과 하루 행동력 상한의 영구 증가가 발생했습니다. 따라서 행동력 차감, 회복, UI 갱신, 날짜 전환의 공통 흐름은 ActionPointManager에서 관리하고, 방별 예외 규칙은 하위 클래스에서 분리했습니다.

---

## 3. 설계 목표

- 하나의 유효한 행동은 행동력을 한 번만 차감할 것
- 이벤트 처리 중 추가 요청을 차단할 것
- 내부 행동력과 화면 상태를 일치시킬 것
- 행동력 소진 시 날짜 전환으로 분기할 것
- 공통 처리와 Room별 규칙을 분리할 것
- 연출과 후속 이벤트의 순서를 유지할 것

---

## 4. 클래스 구조

| 클래스 | 역할 |
| --- | --- |
| `ActionPointManager` | 공통 행동력 검증, 차감, UI 갱신, 날짜 전환 흐름 |
| `Room1ActionPointManager` | Room1의 자원 소비와 전환 규칙 |
| `Room2ActionPointManager` | Room2의 아이템·이벤트와 행동력 규칙 |
| `InteractionObject` | 플레이어 입력과 행동력 감소 요청 연결 |

```text
ActionPointManager
├─ Room1ActionPointManager
└─ Room2ActionPointManager
```

---

## 5. 처리 흐름

```text
상호작용 요청
→ 현재 이벤트 처리 상태 확인
→ 행동력·하트 UI 검증
→ 차감 가능 여부 판정
→ 행동력 차감
→ UI 갱신
→ 남은 행동력 확인
→ 0이면 날짜 전환
→ Room별 연출과 후속 이벤트 실행
```

---

## 6. 핵심 구현

### 6.1 상태 기반 중복 요청 방어

단순한 시간 제한에만 의존하지 않고 이벤트 처리 상태와 행동력·UI 상태를 확인한 뒤 요청을 수락했습니다.

### 6.2 공통 처리와 예외 분리

행동력 감소와 날짜 전환의 공통 절차는 상위 클래스에 유지하고, Room마다 다른 소비 조건과 연출은 하위 클래스에서 재정의했습니다.

### 6.3 날짜별 행동력 데이터

날짜별 행동력 값을 배열로 계산해 현재 날짜 인덱스로 조회했습니다. Save/Load 이후에는 저장된 날짜를 기준으로 행동력과 하트 UI를 복원했습니다.

### 6.4 순차 연출

Coroutine으로 기어, 시계, 페이지, 페이드, BGM과 후속 이벤트를 순서대로 실행했습니다.

---

## 7. 상태 불변 조건

- 행동력은 허용 범위 아래로 감소하지 않음
- 하나의 상호작용은 한 번만 자원을 소비함
- 내부 행동력과 하트 UI가 같은 상태를 나타냄
- 날짜 전환 중에는 추가 요청을 처리하지 않음
- Room별 예외가 다른 Room의 공통 상태에 영향을 주지 않음

---

## 8. 검증 항목

| 항목 | 확인 내용 |
| --- | --- |
| 일반 클릭 | 한 번의 요청으로 행동력이 1만 감소하는가 |
| 반복 클릭 | 빠른 입력에서도 중복 차감되지 않는가 |
| 처리 중 입력 | 연출·이벤트 중 추가 요청이 차단되는가 |
| 자원 소진 | 0 이하로 차감하지 않고 날짜 전환하는가 |
| 자원 회복 | Room2에서 회복 아이템 사용했을 경우 현재 자원과 하루 최대 행동력이 증가하는가 |
| Save/Load | 저장 날짜와 행동력·하트 UI가 일치하는가 |
| Room 규칙 | 한 Room의 수정이 다른 Room에 영향을 주지 않는가 |
| 연출 순서 | 상태 변경과 연출이 지정된 순서로 완료되는가 |

---

## 9. 구현 결과

- 행동력, UI와 날짜 진행을 하나의 상태 흐름으로 통합했습니다.
- 반복 입력에 따른 중복 상태 변경을 방지했습니다.
- 공통 규칙과 Room별 예외의 수정 범위를 분리했습니다.
- 저장 복원 이후 날짜·행동력·UI의 일관성을 보완했습니다.

---

## 10. 한계 및 개선 방향

### 한계

- 내부 상태 검증에 UI 상태가 포함되어 도메인 로직과 화면이 결합됨
- Room이 증가하면 상속 클래스와 재정의 범위가 커질 수 있음
- Coroutine 중단과 취소 정책이 분산될 수 있음

### 개선 방향

- 행동력을 단일 상태 모델로 관리하고 UI는 변경 이벤트 구독
- Room 규칙을 Strategy 또는 데이터 객체로 분리
- 명시적 State Enum/State Machine 적용
- 상태 전환의 Cancellation과 회귀 테스트 자동화

---

## 11. 게임 프로그래밍 역량

요구사항을 공통 절차와 예외 규칙으로 나누고, 실제 입력 경계 조건에서 발생한 상태 불일치를 재현·수정한 경험입니다. 현재 구조의 결합도와 확장 한계를 분석해 후속 리팩터링 방향까지 제시했습니다.
